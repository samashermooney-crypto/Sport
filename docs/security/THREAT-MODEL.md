# Athlentry security threat model

**Status:** engineering draft for Phase 16. Review this model after material
changes to identity, tenancy, payments, files, public content, or deployment.

## Assets and trust boundaries

Athlentry stores children's identity and contact data, guardian relationships,
medical and safety records, financial records, payment-provider references,
staff credentials, sessions, encryption keys, and immutable audit evidence.
The principal boundaries are anonymous/public traffic, a signed-in account,
an organization-scoped actor, platform staff, background workers, PostgreSQL,
private object storage, and external providers. A verified account or an
organization membership does not by itself authorize access to every person or
resource in that organization.

Tenant-owned reads and writes must enter `withOrg`; PostgreSQL forced RLS is
defense in depth. Other-tenant and out-of-scope resource IDs return 404. Access
to a child's records comes from an active `person_account_links` self or
guardian relationship, never descriptive household membership. Restricted
reads and writes are audited, with Restricted values redacted from audit diffs.

## Current residual launch work

- The OpenAPI document does not yet publish permission, resource, or scope
  metadata for every API operation. The permission matrix is empty, so the
  route-authorization, permission-matrix, and route-tenancy completeness specs
  remain `test.fixme`. Track C owns generated route metadata and CI; the
  current request is recorded in both track files. The class-specific route
  journey proves GET and schema-valid PATCH isolation for one existing foreign
  offering ID, but does not replace the all-route SEC-002 contract.
- Gitleaks is configured in CI, but the hosted scanner run has not been
  observed from this local environment. Organization-owned repositories must
  supply the `GITLEAKS_LICENSE` repository secret.
- Step-up reauthentication rotates and revokes the old cookie/bearer session;
  `/step-up` and MFA enrollment confirmation consume the shared MFA rate limit.
  Auth tests and the Chromium fixation journey provide local evidence.
- `WebPushSender` accepts only supported provider hosts, verifies every DNS
  answer is globally routable, and pins the transport to the validated IP.
  Sender tests cover private and transition ranges, mixed DNS answers, and
  rebinding; the Chromium SSRF regression covers the loopback endpoint.
- `npm audit --omit=dev --audit-level=high` found no high or critical
  advisories; it reports two moderate transitive `uuid` advisories under
  `exceljs`. `npm run knip` reports 6 unused files, 43 unused exports, 28 unused
  types, and one duplicate export across A/C/G/I-owned files; cleanup requests
  are recorded in the owner track files.
- `server/src/app.ts` mounts the shared security headers before API and static
  routes. HSTS is production-only, and framing is denied except on the explicit
  embed surface. The app also mounts Stripe raw-body ingress before feature
  routers; signature verification rejects modified bytes.
- The security.txt handler serves the draft in development and fails closed in
  production until deployment supplies a staffed `mailto:` contact and HTTPS
  policy URL. Replace the reserved `.example` address and domain before
  publishing a public contact channel.
- This model is not a penetration test, legal review, or provider assurance.
  Complete those human/operator steps before production launch.
